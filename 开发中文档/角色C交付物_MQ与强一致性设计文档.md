## 2. 核心架构与一致性机制实现

### 2.1 事务消息与异步持久化 (Outbox Pattern)
出于性能考虑，高并发下的写请求并不直接冲击 MySQL 数据库。
- **发件箱模式 (Outbox)**：业务操作在确认后写入本地或缓存中的发件箱（Outbox），并由异步任务投递至 MQ（本项目采用了 Redis Stream 模拟高性能中间件队列）。
- **消费者批量写入 (`VoteEventConsumer`)**：后台线程按微批次（Batch）拉取事件流，以 `app.vote.mq-batch-size=100` 为阈值执行批量写入 MySQL，极大减轻了 DB 的并发写入压力。

### 2.2 强一致性控制验证 (分布式锁与精确库存)
- **并发互斥**：在进行关键扣减行为时，利用 `RedlockService` 锁定特定的 `option_id` 或 `poll_id`。
- **库存防止超卖**：采用 `Redis Lua` 脚本进行操作，保证条件判断（库存大于0）和扣减动作的强原子性。

### 2.3 数据一致可见性 (读写锁)
为确保大屏请求获取到的排名结果与写操作并行时不发生严重错乱，采用了内存级别的 `ReadWriteLock` 控制（即在生成并缓存排名时加入读写锁隔离），完美规避脏读问题。

### 2.4 幂等消费防复 (Idempotency)
- **提交去重**：用户端接口使用 `voterId` 或 `userId` 加上限制窗口的 TTL 防护，避免疯狂点击。
- **消费去重**：消费者引入了 `VoteIdempotencyService`，底层使用 `Redis SETNX` 存储唯一事件 UUID (`eventId`)，即使 MQ 因网络波动重复推送同一条日志，也不会引起数据库复写。

### 2.5 容错回退与死信队列 (DLQ)
如果消息格式异常或者发生无法预料的数据死锁，单条消费会路由转入 `vote.event.dlq.stream`。
系统针对管理端暴露了手工干预口（如 `/api/votes/admin/dlq/retry`），以允许运营人员或运维自动化修复。

## 3. 灾备重建与读修复 (Data Recovery)

这也是本系统数据持久化的终极防线：即当 Redis 节点整体损毁（断电、数据强制刷空）时，可以通过 MySQL 的归档数据完美重启服务。

1. **自动快照 (`VoteRecoveryService.createSnapshot`)**：后台默认每 300000 毫秒 (5 分钟) 将汇聚后的统计数据刷入数据库作为时间锚点快照 (`vote_count_snapshot`表)。
2. **读修复 / 缓存重建 (`/api/votes/admin/recovery/rebuild`)**：利用最近一次 Snapshot 快照，结合快照时间后的零散 `VoteEvent` 增量事件单条回放，反向从 MySQL 逐项写入 Redis 内存中。

## 4. 环境规范与端到端实测报告

### 4.1 云原生容器部署
项目不再局限于本地运行环境，采用 `docker-compose` 进行完全隔离和自动编排：
```bash
# 构建镜像并自动协同 MySQL、Redis 启动集群
docker-compose up -d --build
```
所有微服务环境变量均被注入到容器内部连通，实现了云端快速迁移能力。

### 4.2 环境测试验证报告
基于以上功能，于容器化环境实施了以下端到端用例测试并 **全部通过**：
1. **库存准确性测试**：限定库存提交时，能准确写入 Redis 和发送 Stream，没有出现负数库存的超发问题。
2. **全链路异步落库验证**：投出的票数被系统返回成功后，在等待约半秒被 `VoteEventConsumer` 消费者从 Stream 捞出并永久落地至 MySQL，读写锁下前端查询无延迟。
3. **完全宕机与零丢失的读修复测试**：
   - 触发 Redis 清除命令 `FLUSHALL` 抹除所有计票内存。
   - 调用数据恢复暴露层通过 MySQL 数据库重建整个系统。
   - 重建完成后数据分毫不差地 1:1 恢复至 Redis：精确重构出了选项的库存与累积票数结果，验证了“基于最终一致性的高可用灾备方案”实现。

> **注:** 本部分所涉及的后端运维暴露接口（`/api/votes/admin/...`），皆为本负责板块为了配合前端（角色D）触发数据修复或者管理端手动修复要求所自研的支持性控制层，用于对接验证测试。
